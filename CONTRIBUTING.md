# Работа в команде

Основные ветки: `main` (релиз, default) и `develop` (интеграция).
Одна задача = одна короткая ветка от свежей `develop` = один PR в `develop`.
Ветки: `codex/21-fe-upload`, `codex/22-api-projects`, `codex/23-render-ass`.
Номер берите из реальной issue. Постоянные ветки на человека или подсистему не нужны.

1. Назначьте исполнителя и ревьюера, запишите приёмку и зависимости в issue.
2. Реализуйте небольшой результат, обновите комментарии TODO и документацию.
3. Прогоните проверки своей части из README. Изменение DTO требует проверки frontend и backend.
4. В PR укажите `Refs #номер`, сценарий проверки и ограничения; приложите доказательство результата.
5. Другой участник проверяет diff и поведение. После зелёного CI и approval используйте **Create a merge commit**.
6. Татьяна проверяет интеграцию на `develop`, записывает SHA и результат в issue. Только после этого закрывает её.
7. Изменения самой Татьяны проверяет Андрей, а сквозной сценарий - Леонид или Руслана.

Не переписывайте опубликованную историю. Для обновления своей ветки: `git fetch origin`,
затем `git merge origin/develop`. Конфликт решайте с владельцем файла.
Не используйте force push. Не удаляйте `main` и `develop`.

Файлы, треки пользователей, секреты, `.env`, модели ML и сборки не коммитятся.
Проверяйте `git diff --staged` до коммита. Lock-файлы входят в Git.
Шрифт/демоматериал добавляется вместе с источником и лицензией.

Сейчас это каркас. Зелёный CI означает работоспособность каркаса, а не готовность v0.
Критерий готовности функции: поведение реализовано, есть нужная проверка, review, интеграционный ретест и обновлённая документация.

Подробные команды: [GitHub](docs/github.md). Владельцы: [команда](docs/team.md).
