Номера с точкой (например, F1.01) обозначают шаги по функциям.
ID с дефисом в backlog/GitHub обозначают более крупные задачи; это разные уровни плана.

Этот файл описывает **что ещё написать** поверх существующего каркаса. Наличие функции или зелёного теста не означает готовности пользовательского сценария. Функции с `TODO` выбрасывают ошибку либо показывают заглушку; рабочие утилиты отмечены отдельно. Имена участников взяты из презентации; распределение подтверждается командой.

### F1.02. Согласовать DTO и `request<T>()`

**Файлы:** `frontend/src/shared/types/project.ts`, `frontend/src/shared/api/client.ts`, `docs/api.md`.

**Уже есть:** типы `Project`, `LyricLine`, `LyricsDraft`, `RenderJob`, `QueuedRender`; `request<T>(path, options)` отправляет fetch и возвращает Promise JSON. `ApiError` хранит HTTP status и `details` с `code/message/field`. У FormData браузер сам выставляет boundary. Ответ 501 не превращается в успех.

**Что сделать:** с B1 сверить каждый ключ и null-поле на реальном OpenAPI; проверить envelope ошибок. Не переименовывать ключ только в TypeScript. В компонентах отличать `ApiError` от отсутствия сети; показывать `message`, а ошибку с `field` направлять к соответствующей строке. AbortError при уходе со страницы не показывать как ошибку пользователю. Не хранить токен сессии в localStorage; cookie обрабатывает браузер.

**Вход/выход:** относительный путь без `/api/v1`, параметры fetch → JSON ожидаемого DTO либо исключение. Тип `T` — compile-time договор, не валидация JSON на исполнении.

**Проверка:** 422 содержит исходные code/field, 501 виден как неготовая функция, HTML-ошибка прокси даёт понятную HTTP-ошибку, обрыв сети не создаёт фиктивный объект. **Зависимости:** B1 схемы и обработчик ошибок. **Передать:** F2 — стабильный клиент; QA — примеры ответов.

**Проверка:** последовательность queued→running→succeeded прекращает запросы; failed тоже прекращает; уход со страницы отменяет запрос/таймер; плохая сеть не вызывает POST. **Зависимости:** F1.06. **Передать:** `ResultPage()`, QA сценарий отключения сети.

### F1.08. Подключить `ResultPage()`

**Файл:** `frontend/src/features/render/ResultPage.tsx`.

**Что написать:** по project id из URL получить project, затем latest_job_id; при отсутствии job показать предложение вернуться к редактору. Запустить pollJob с cleanup. Отдельные состояния: loading, queued, running, succeeded, failed, network-error. Для queued/running вывести честное ожидание без процентов. На сетевой ошибке кнопка повторяет GET того же job; при failed кнопка нового рендера отдельно проверяет актуальный draft. Показать, если успешный результат относится к прежней revision, после согласования поля снимка с B2.

**Вход/выход:** project id → состояние существующей задачи и переходы пользователя. **Проверка:** F5 на result восстанавливает job; поздний ответ старого job не заменяет текущий; ошибка не скрывает кнопку редактора. **Зависимости:** F1.07, B1 latest_job_id, B2 статус/revision снимка. **Передать:** F1.09, QA.

## Как сдавать совместную работу

1. Перед изменением DTO открыть вопрос в issue и согласовать с B1/B2; обновить TypeScript, Python и docs/api вместе.
2. F1 не меняет внутреннее состояние редактора без F2; F2 использует единый API-клиент и CSS.
3. F1 ревьюит F2, F2 ревьюит F1. B1/B2 смотрят PR, который меняет контракт. Татьяна A2/QA проверяет интегрированный результат, не только скриншот компонента.
4. В PR: Refs #issue, что теперь работает, какой API нужен, точные шаги проверки, результат lint/test/build, ограничения.
5. После merge приложить SHA и сценарий QA. Задача Done только после проверки поведения; наличие функции и компиляция недостаточны.

## Что проверять перед каждым frontend PR

```powershell
cd frontend
npm ci
npm run lint
npm run test -- --run
npm run build
```

При изменении DOM дополнительно вручную пройти изменённый экран клавиатурой. При API-интеграции запустить настоящий backend и показать запрос/ответ. Unit-тесты писать на значимое поведение: порядок await, обработку ошибок/отмены, редактирование без потери таймингов. Не подменять сквозной тест моками и не добавлять тест «TODO выбрасывает TODO» как доказательство функции.
