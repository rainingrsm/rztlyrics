# Задания backend: Руслана (B1) и Варвара (B2)

Этот файл описывает работу, которую ещё предстоит выполнить. Сейчас реализованы только
диагностика, DTO, часть валидации, начальная миграция и запуск пустого RQ worker.
Продуктовые обработчики возвращают `501`; функции-заготовки бросают `NotImplementedError`.
Зелёные тесты каркаса не означают, что загрузка, сохранение или рендер работают.

Названия вида `B1-01` являются метками плана. Создайте настоящие GitHub issues и впишите
их номера в PR. Точки входа ниже уже существуют в репозитории; новые вспомогательные
функции добавляйте только при необходимости. Не надо писать собственный ORM, framework
очередей или общий «универсальный сервис».

В общем backlog карточки укрупнены: B2-01 включает инфраструктуру, B2-02 - задания,
B2-03 - видео, B2-04 - готовность стенда. Ниже восстановление задач и очистка являются
подзадачами B2-04, а не отдельным переопределением карточки. Названия функций внутри
карточки можно перенести в её checklist; отдельный issue на каждую функцию не требуется.

## Шаг 1. Зафиксировать данные и запустить основу

**Вход:** этот каркас, согласованные `docs/api.md`, ограничения v0 и пример разметки.
**Выход:** все участники запускают один API, видят одну OpenAPI и используют миллисекунды.

1. Руслана и Варвара читают `backend/app/schemas/projects.py` и `jobs.py` вместе с F1/F2/A2.
   Подтверждают поля `ProjectResponse`, `LyricsUpdate`, `RenderAccepted`, `JobResponse`.
   UUID передаётся строкой; время - целым числом миллисекунд; пропущенное время - `null`.
2. В `backend/app/config.py` функция `get_settings()` уже читает окружение. Проверить
   `DATA_DIR`, `DATABASE_URL`, `REDIS_URL`, `APP_VERSION`, `COMMIT_SHA`,
   `SESSION_COOKIE_SECURE`. Локально данные идут в корневой `data/`, Docker использует
   `/data`. `.env` подхватывает Compose; при локальном Python переменные задают отдельно.
3. В `backend/app/db.py` функции `get_engine()` и `new_session()` уже создают движок
   с WAL, foreign keys и busy timeout. Подключение пока рассчитано на SQLite. Использовать
   `with new_session() as session:` и короткую транзакцию. Не держать её во время ffprobe,
   FFmpeg, чтения загрузки или сетевого обращения к Redis.
4. В `backend/app/models/entities.py` проверить `ProjectRecord`, `LyricLineRecord`,
   `RenderJobRecord` и `utc_now()`. `position` хранит порядок строк; `revision` показывает
   изменение черновика; `snapshot` задания хранит независимые от черновика данные.
   `owner_session_hash` хранит hash сессии, а не cookie в исходном виде.
5. Выполнить `uv sync --frozen`, затем `uv run alembic upgrade head` из `backend/`.
   `backend/migrations/env.py:run_migrations_online()` использует тот же движок.
   `run_migrations_offline()` формирует SQL без подключения. Функция
   `backend/migrations/versions/0001_initial.py:upgrade()` уже создаёт таблицы и индекс
   `uq_active_job_per_project`; он допускает лишь одну queued/running задачу проекта.
6. Выполнить `uv run alembic check`. Если модели потребуется изменить, создать новую
   миграцию `uv run alembic revision --autogenerate -m "describe_change"`, прочитать её
   вручную, проверить upgrade на отдельной тестовой БД. Не переписывать применённую у
   коллег миграцию. `downgrade()` удаляет данные: проверять откат только на тестовой БД.
7. Проверить `backend/app/main.py`: маршруты имеют `/api/v1`, документация `/api/docs`,
   OpenAPI `/api/openapi.json`. В `api/health.py:health()` сейчас проверяется только жизнь
   API; это не доказательство работоспособности Redis/БД/FFmpeg. `version()` отдаёт
   версию, SHA и пометку `stage=scaffold`; убрать эту пометку при фактической готовности.

**Проверка:** чистый запуск, миграция без ошибки, OpenAPI открывается, `alembic check`
не находит расхождений, стандартные значения окружения одинаковы в README и Compose.
**Передача:** F1/F2 получают URL и пример JSON; A1/A2 - формат времени и snapshot.
**Готово:** контракты приняты в одном PR, команды повторены другим участником.

## B1-01. Анонимная сессия и проекты

**Ответственная:** Руслана. **Проверяет:** Варвара; F1 проверяет контракт интерфейса.
**Зависимость:** шаг 1. **Вход:** HTTP-запрос без аккаунта. **Выход:** собственный проект,
который можно восстановить по URL в том же браузере.

### `backend/app/services/sessions.py:get_or_create_session(request, response)`

1. Если корректная cookie уже есть, использовать её. Если нет - создать случайный токен
   через `secrets`, а не UUID проекта, email или текущую дату.
2. Поставить cookie с `HttpOnly`, `SameSite=Lax`, `Path=/`; `Secure` включать на HTTPS.
   Срок cookie согласовать со сроком хранения проектов. Для локального HTTP значение
   `SESSION_COOKIE_SECURE=false`, иначе браузер может не передать cookie.
3. Вернуть SHA-256 hash токена; в базе хранить именно его. Не писать токен в логи,
   ответы API или URL. Случайный токен служит единственным ключом доступа к проектам.
4. До подключения метода решить поведение некорректной cookie: при создании нового
   проекта выдать новую; при чтении чужого URL не создавать сессию незаметно.

**Проверка:** первый POST ставит cookie, второй использует ту же; HttpOnly присутствует;
разные TestClient-сессии получают разный доступ. **Готово:** F1 не передаёт владельца
в JSON и не хранит секрет сессии в localStorage.

### `backend/app/services/sessions.py:require_session(request)`

1. Прочитать существующую cookie, проверить допустимую длину/формат.
2. Если её нет или она некорректна, вернуть ту же ошибку 404, что для неизвестного проекта.
3. Вернуть hash. Не создавать cookie и не проверять доступ только по UUID объекта.

**Проверка:** GET без cookie не открывает известный UUID; отсутствующая сессия не создаёт
новую запись. **Передача:** B2 использует эту функцию для всех заданий и MP4.

### `backend/app/services/projects.py:create_project(owner_session_hash)`

1. Создать UUID сервером, `ProjectRecord` со стилем `brat`, `revision=0`, пустыми audio и
   duration; установить created/updated UTC. Добавить запись и завершить транзакцию.
2. Вернуть `ProjectResponse`: `lines=[]`, `audio_url=null`, `duration_ms=null`,
   `latest_job_id=null`. В ответе нет hash сессии и файловых путей.
3. Ошибку записи обрабатывать как серверную ошибку без SQL и внутренних путей в ответе.

**Проверка:** 201, разные UUID, запись остаётся после нового подключения к БД.
**Передача:** F1 получает id для следующего POST аудио.

### `backend/app/services/projects.py:load_project(project_id, owner_session_hash)`

1. Найти проект одновременно по id и владельцу. Нет совпадения - 404 без уточнения,
   существует ли такой id у кого-то другого.
2. Загрузить строки по `position`, преобразовать nullable times без замены `null` на `0`.
3. Сформировать защищённый `audio_url` только если файл загружен. Вернуть latest job и
   revision; не отдавать каталог `/data` как публичную статику.

**Проверка:** чтение своего/чужого/несуществующего проекта; порядок строк; пустой проект.

### `backend/app/api/projects.py:create_project()` и `get_project(project_id)`

1. Добавить HTTP `Request`/`Response` или простые зависимости FastAPI для сессии.
2. Заменить соответствующий `not_implemented(...)` вызовом сервисных функций.
3. Сохранить response_model, статусы 201/200 и единый формат ошибок. Не дублировать
   SQL и проверку cookie в каждом обработчике.

**Проверка всей задачи:** через реальный клиент создать проект, запомнить URL, открыть его
в той же сессии и в другой. **Готово:** F1 умеет создать проект, B2 умеет проверить владельца;
в PR есть запросы/ответы и тесты доступа.

## B1-02. Аудиофайл, ограничения, перемотка

**Ответственная:** Руслана. **Проверяет:** Варвара; A1 помогает с ffprobe.
**Зависимость:** B1-01. **Вход:** `multipart/form-data`, поле `file`, id своего проекта.
**Выход:** сохранённый MP3/WAV, точная длительность и защищённый URL аудио.

### `backend/app/services/audio.py:store_audio(project_id, upload, owner_session_hash)`

1. Проверить владельца и отсутствие уже загруженного аудио. При повторной замене вернуть
   409: в v0 пользователь создаёт новый проект, старые тайминги не переиспользуются молча.
2. Создать серверный каталог `DATA_DIR/projects/<UUID>/`. Имя из `upload.filename`
   использовать только для диагностического сообщения после очистки, никогда как путь.
3. Читать файл порциями, считать реально полученные байты. После превышения
   `MAX_AUDIO_BYTES=20*1024*1024` остановиться, удалить временный файл, вернуть 413.
   Не полагаться только на `Content-Length`, расширение или MIME браузера.
4. Запустить ffprobe списком аргументов с `shell=False` и timeout. Проверить реальный
   контейнер/декодируемый аудиопоток, разрешённые MP3/WAV и отсутствие некорректных
   duration. Длительность привести к целым миллисекундам единым согласованным способом.
5. Принять только 5000-60000 мс включительно. Повреждённый файл/неверный формат и
   выход за длительность возвращают согласованные ошибки 415/422. Пустой файл отклонить.
6. Атомарно переименовать проверенный временный файл в серверное имя и записать путь/
   duration в проект. Если БД не обновилась, убрать оставшийся файл. Не держать транзакцию
   на протяжении загрузки или ffprobe. При конкурентной загрузке не перезаписать первый
   файл; финальное изменение проекта сделать условным/атомарным.
7. Закрыть `UploadFile` и временные ресурсы во всех ветках. Вернуть duration; маршрут затем
   получает обновлённый `ProjectResponse` через `load_project()`.

**Проверка:** настоящий WAV/MP3; переименованный текст; пустой файл; повреждённый заголовок;
ровно/больше 20MiB; 5/60с и выходы за границы; имя `../../outside.wav`; два одновременных POST.
После любой ошибки не остаётся доступного мусорного файла и не портится уже сохранённый.

### `backend/app/services/audio.py:get_audio_path(project_id, owner_session_hash)`

1. Загрузить свой проект, проверить наличие audio_path и файла.
2. Разрешить абсолютный путь и проверить, что он лежит внутри каталога данных проекта.
3. Вернуть `Path` только внутреннему обработчику. Не превращать ошибку доступа в выдачу
   любого файла, указанного клиентом.

**Проверка:** чужая сессия/отсутствующий файл -> контролируемая ошибка; корректный путь
доступен только собственнику. **Передача:** F2 получает аудио для таблицы таймингов.

### `backend/app/api/uploads.py:upload_audio()` и `get_audio()`

1. `upload_audio()` связывает require_session, store_audio, load_project и возвращает 200.
2. `get_audio()` проверяет сессию, вызывает get_audio_path и возвращает `FileResponse`
   с подходящим media type. Проверить поддержку Range выбранной версией response.
3. Написать тест `Range: bytes=0-99`: ответ 206 с `Content-Range`, не весь файл. Проверить
   обычное чтение 200 и отказ чужому браузеру до отдачи любых байтов.

**Готово:** F1 загружает разрешённый файл, F2 слушает и перематывает его после F5;
A1 может получить проверенный серверный путь для renderer. Разделять проверку того,
что загрузка принята, и того, что браузер реально проигрывает её.

## B1-03. Черновик текста и таймингов

**Ответственная:** Руслана. **Проверяют:** Варвара, F2; A2 сверяет правила.
**Зависимость:** B1-01; при проверке границ времени нужна B1-02.
**Вход:** `LyricsUpdate`. **Выход:** сохранённый `ProjectResponse` с новой revision.

### `backend/app/schemas/projects.py`: существующие правила

- `LyricLine.reject_blank_id()` отклоняет идентификатор из одних пробелов. Поле id
  ограничено 1-64 символами; это же ограничение проверяют frontend и renderer.
- `LyricLine.reject_blank_text()` отклоняет строку из пробелов. Внешние пробелы сейчас
  сохраняются; изменение политики согласовать с frontend, не обрезать текст неожиданно.
- `LyricLine.validate_interval()` проверяет длину >=100мс, если обе границы уже заданы.
  `Milliseconds` использует strict int: дроби, boolean и строка `"100"` не принимаются.
- `LyricsUpdate.validate_line_ids()` отклоняет повтор id, но допускает одинаковый текст.
  Пустой список и отдельные null времена допустимы для сохранения незаконченного draft.
- `validate_render_ready(draft,duration_ms)` запрещает пустой текстовый набор, null времена,
  пересечения, нарушенный порядок и конец за пределами аудио. Интервалы `[start,end)`:
  соседняя строка может начинаться ровно в конце предыдущей; паузы допустимы.

**Работа:** не переписывать эти функции с нуля. Добавить тесты недостающих граничных случаев,
сверить их с чистой валидацией A2 в renderer. Одни и те же fixtures должны давать одинаковый
результат. Ошибку render-ready преобразовывать в `INVALID_TIMING` с точным `field`, не
показывать пользователю traceback или только общий текст без строки.

### `backend/app/services/projects.py:save_draft(project_id, owner_session_hash, draft)`

1. Проверить владельца и допустимый стиль. При известной duration проверить заданные
   границы по длине аудио; неполные строки разрешить сохранить. Отдельно договориться
   с A2/F2, какие ошибочные черновики сохраняем: текущая схема запрещает полностью
   заданный интервал короче 100мс, но итоговые пересечения проверяет перед render.
2. В короткой транзакции заменить строки проекта, выставив `position` по входному порядку;
   сохранить id текста и null без потерь. Увеличить revision и обновить updated_at.
3. Не менять `RenderJobRecord.snapshot` ранее запущенных задач. Старая задача принадлежит
   старой revision, даже если пользователь редактирует текст прямо сейчас.
4. Сформировать ответ из сохранённых данных. Отправить 200 только после commit, иначе
   frontend может начать рендер несохранённого текста.

**Проверка:** F5; пустой draft; null и начало 0; кириллица/кавычки/слеши; 100/101 строка;
120/121 символ; одинаковый текст с разными id; неуспешное сохранение не стирает старый draft.

### `backend/app/api/projects.py:save_lyrics(project_id,payload)`

1. Подключить require_session и save_draft, убрать заглушку этого обработчика.
2. Не принимать от frontend owner/path/duration; сервер знает их из своего проекта.
3. Сохранить формат ответа. Договориться с F2: сначала дождаться PUT 200, только затем POST renders.

**Готово:** редактор восстанавливается после F5; B2 может загрузить complete draft для снимка.

## B2-01. Очередь и среда исполнения

**Ответственная:** Варвара. **Проверяет:** Руслана; A1 проверяет FFmpeg внутри того же образа.
**Вход:** Compose и env из корня. **Выход:** один API-процесс и один worker с общим `/data`.

### `backend/app/tasks/worker.py:main()`

1. Запустить существующий модуль в Linux с Redis; он слушает очередь `renders`, default
   timeout 300с. Не пытаться заставить основной RQ Worker работать нативно в Windows.
2. Убедиться, что api и worker получают одинаковые DATA_DIR/DATABASE_URL и общий volume.
   Redis хранит очередь, а SQLite - долговечные сведения о проектах и задачах.
3. Добавить необходимый контроль startup/recovery из B2-04 до production-приёмки.
   Не вызывать reconcile безусловно так, чтобы другой живой worker считался потерянным.
4. Вместе с A1 проверить ffmpeg, ffprobe, libass, H.264/AAC и кириллический шрифт внутри
   worker-образа. Установка FFmpeg на Windows-хосте не доказывает готовность контейнера.

**Проверка:** worker виден в логах Redis/RQ, API отвечает без ожидания FFmpeg; перезапуск не
удаляет volume. **Готово:** A1 запускает свою функцию в том же окружении, что будущая очередь.

## B2-02. Снимок, постановка задания, статусы

**Ответственная:** Варвара. **Проверяет:** Руслана; F1 проверяет опрос.
**Зависимости:** B1-01, B1-03, B2-01. **Вход:** id своего проекта с сохранённой разметкой.
**Выход:** `202 {job_id,status:"queued"}` и последующее состояние этого задания.

### `backend/app/services/renders.py:enqueue_render(project_id,owner_session_hash)`

1. Проверить владельца, наличие проверенного аудио, style и `validate_render_ready()`.
   Снимок включает revision, duration_ms, style, массив строк с полными временами и
   серверную связь с неизменяемым аудио. Уточнить формат вместе с A1/A2 до кода worker.
2. В транзакции создать `RenderJobRecord` со своим UUID/status=queued/snapshot и обновить
   latest_job_id проекта. Ошибка unique active index -> 409. Проверка `if no job` перед
   INSERT сама по себе не защищает от одновременных запросов.
3. Завершить транзакцию, передать в RQ `app.tasks.render_job.run_render_job` и серверный id.
   RQ job id сделать равным id записи; не передавать пользовательскую строку как имя функции.
4. Обработать недоступный Redis: перевести созданную запись в failed с кодом QUEUE_UNAVAILABLE,
   вернуть 503. Разобрать окно «БД commit прошёл, процесс упал до enqueue» через reconcile.
5. Если результат enqueue неопределён из-за сети, проверить существование RQ job с этим id,
   не создавать второй рендер вслепую. Не обещать exactly-once; handler должен защититься
   от повторного выполнения и не перетирать успешный результат.
6. Вернуть 202 только после подтверждённой постановки. Ограничение длины очереди/429
   добавить здесь до общего доступа; число активных вычислений v0 = один worker.

**Проверка:** два параллельных POST дают одну активную запись; null times -> 422 без job;
Redis отключён -> 503, запись не висит queued навечно; последующая правка draft не меняет snapshot.

### `backend/app/services/renders.py:load_job(job_id,owner_session_hash)`

1. Читать RenderJob вместе с владельцем его проекта. Чужая/несуществующая задача -> 404.
2. queued/running: video_url=null,error=null. succeeded: защищённый video_url; failed:
   безопасные code/message. Не отдавать полный stderr, системные пути или сырой exception.
3. Состояние брать из долговечной записи БД; не считать отсутствие Redis result доказательством
   отсутствия завершённого видео. TTL Redis и срок хранения результата - разные вещи.

**Проверка:** четыре состояния и чужая сессия; ответы соответствуют `JobResponse`.

### `backend/app/api/renders.py:start_render()` и `api/jobs.py:get_job()`

1. Добавить require_session и соответствующий сервис, убрать 501 только для готовых операций.
2. POST возвращает 202 быстро; длительная работа не выполняется в HTTP request/BackgroundTasks.
3. F1 опрашивает GET раз в ~2с и при сетевом сбое повторяет GET с тем же job_id, а не POST.

**Готово:** API и frontend видят одну задачу и различают ошибку сети от failed рендера;
есть интеграционный тест двойного запуска и документированный sample response.

## B2-03. Настоящий MP4 и выдача результата

**Ответственная:** Варвара. **В паре:** Андрей A1; **проверяет:** Руслана и A2.
**Зависимости:** B1-02, B1-03, B2-02, работающий renderer. **Выход:** скачиваемый MP4.

### `backend/app/tasks/render_job.py:run_render_job(job_id)`

1. Загрузить задачу из БД. Атомарно перевести queued -> running, записать started_at.
   Повторный вызов для succeeded/running не запускает второй FFmpeg.
2. Создать каталог `DATA_DIR/jobs/<UUID>/`; получить проверенный путь аудио. Построить
   `renderer.models.RenderSpec` и `LyricLine` из snapshot, не из текущего проекта.
3. Импортировать `LyricLine`, `RenderSpec`, `render_video` из пакета `renderer` и вызвать
   `render_video(spec,audio_path,output_path)`. API, Redis и SQLAlchemy туда не передаются.
4. Renderer пишет временный файл, проверяет его и атомарно публикует итог; B2 принимает
   `RenderResult`, проверяет существование результата и только затем ставит succeeded.
   Публичный интерфейс пакета закреплён в `backend/renderer/__init__.py`.
5. Любая штатная ошибка -> failed, code/message, finished_at. Лог хранится отдельно,
   в API попадает безопасное объяснение. Неполный файл нельзя публиковать как video_url.
6. Внутренний timeout FFmpeg меньше RQ timeout (например 240с < 300с). Вместе с A1
   проверить завершение дочернего процесса и временные файлы при обоих типах timeout;
   одного try/except недостаточно при принудительной остановке процесса worker.
7. Завершить транзакции до/после вычисления. Никакой открытой транзакции на весь рендер.

**Проверка:** реальный 5-10с fixture -> H.264/AAC/yuv420p/1280x720/30fps; две задачи
последовательно; исключение renderer; timeout; остановка worker; повтор после failed.
Строки по snapshot не меняются, если в редакторе сохранили другой текст.

### `backend/app/services/renders.py:get_result_path(job_id,owner_session_hash)`

1. Найти задачу только в своём проекте. Чужая/неизвестная -> 404, неготовая -> 409.
2. Для succeeded проверить файл и разрешённый абсолютный путь внутри каталога job.
   Отсутствующий файл не выдавать как success; зафиксировать контролируемую ошибку.
3. Вернуть внутренний Path. Не использовать video_url из запроса как путь.

### `backend/app/api/jobs.py:get_video(job_id,download=False)`

1. require_session -> get_result_path -> `FileResponse(media_type="video/mp4")`.
2. Для просмотра поддержать Range и inline, для `?download=1` выставить attachment
   с безопасным серверным именем `rzt-<job_id>.mp4`.
3. Не требовать от фронтенда скачивать весь MP4 через JSON/base64. Браузер использует URL
   с cookie. Прокси не должен удалять Range/Content-Range или терять cookie.

**Проверка:** video controls играет и перематывает; download сохраняет MP4, который открывается
вне сайта; 206 на Range; другая сессия не получает байты. **Готово:** F1 и A2 проходят
полный путь загрузка -> текст -> тайминги -> render -> просмотр -> скачать на стенде.

## B2-04. Сбои, очистка и повтор

**Ответственная:** Варвара. **Проверяет:** Руслана; A2 ведёт сценарии приёмки.
**Зависимость:** B2-03. **Выход:** понятный failed вместо вечного ожидания, сохранные черновики.

### `backend/app/services/renders.py:reconcile_interrupted_jobs()`

1. Определить, когда вызывается сверка: при старте сервиса и регулярно отдельной явной
   командой/планировщиком. Зафиксировать решение в README; одно объявление функции её не запускает.
2. Сопоставить active записи SQLite с RQ очередью, running registry/worker heartbeat и
   установленными timeout. Недоступный Redis означает «не удалось проверить», а не
   разрешение объявить все задания failed.
3. Отметить подтверждённо потерянные задания failed с кодом INTERRUPTED; сохранить
   snapshot/черновик для ручного повторного POST. Вернуть число изменённых записей.
4. Сверку делать безопасной для повторного запуска; чужой работающий worker не останавливать.

**Проверка:** API restart не ломает работающий render; kill worker -> задача становится failed
после сверки; повтор создаёт новую задачу; успешный MP4 и черновик остаются после restart.

### `backend/app/services/cleanup.py:cleanup_expired_projects(retention_hours=24)`

1. Выбрать истёкшие проекты по согласованному времени updated_at; исключить queued/running

2. Добавить режим предварительного просмотра списка кандидатов перед реальным удалением.
   Перед удалением каждого пути resolve и проверить принадлежность DATA_DIR; никогда
   не строить shell-команду удаления из пользовательского значения.
3. Проверить активные jobs повторно непосредственно перед удалением, согласовать порядок
   удаления файлов/записей и восстановление после частичного сбоя. Операция идемпотентна.
4. Возвращать число удалённых проектов, логировать только технические id/итог. Настроить
   регулярный запуск; показать пользователю срок хранения в UI/README.

**Проверка:** истёкший проект удалён; активный job и свежий проект сохранены; повтор не падает;
путь вне data не удаляется. Тестировать только на отдельном каталоге, не на demo-стенде.

**Готово B2-04:** A2 повторяет documented restart/cleanup сценарии; данные не теряются

## Ошибки и проверки перед передачей

`backend/app/errors.py:register_error_handlers()` уже приводит HTTP и Pydantic ошибки
к `{"error":{"code","message","field"}}`. Вложенные `handle_http_error()` и
`handle_validation_error()` служат одной точкой форматирования. Функция
`not_implemented()` нужна только оставшимся заглушкам; не перехватывайте её, чтобы вернуть 200.

При внедрении сервисов согласовать коды: 404 unknown/foreign, 409 active job/reupload,
413 bytes limit, 415 format, 422 invalid data/timing, 429 queue limit, 503 unavailable queue.
Схема `ErrorDetail` в `schemas/jobs.py` описывает также ошибку failed задания. Не возвращать
статус succeeded и поле error одновременно. Не скрывать необработанные server exceptions
под «файл не подходит»: настоящие сбои должны попадать в технический лог.

Руслана расширяет `backend/tests/test_api.py` и `test_schemas.py`: временная БД, собственные
client cookies, fixture-файлы, доступ/загрузка/сохранение. Варвара добавляет отдельные tests
заданий/результата с изолированной Redis/БД, timeout и повтором. Не подменять интеграционный
тест рендера только mock; mock полезен для веток ошибки, настоящий MP4 нужен отдельным прогоном.

Перед каждым PR из `backend/`:

```powershell
uv run ruff check .
uv run ruff format --check .
uv run pytest
uv run alembic check
```

`alembic check` предполагает применённые миграции. Указать в PR: issue, что теперь
реализовано, что ещё 501, входной пример, результат теста, кому передан интерфейс.
После merge A2 проверяет интегрированный стенд и записывает SHA/результат. Только после
этого задачу закрывают; один зелёный pytest не заменяет проверку браузера и MP4.
